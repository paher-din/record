## 1. Purpose

Prove non-destructive upgrade into the generation layout, complete logical backup, overwrite restore, recovery, and explicit migration ownership without relying on CSV or Android system transfer. The P5 exit gate includes the `GENERATION_BOOTSTRAP` v1/root-layout compatibility matrix; an automated export → wipe/overwrite → restore → startup comparison that matches every fact, relation, assignment, balance, attachment owner, size, and SHA-256; every binding ZIP entry/path/size/staging/ratio limit passing declared and streamed boundary tests; `BACKUP_STREAM_AND_PUBLISH`, `BACKUP_SAF_COPY`, `RESTORE_ACTIVATION`, and applicable `MIGRATION_RECOVERY` fault evidence; and source manifest, merged manifest, final APK, API 34 extraction rules, and compatible rules that exclude all app user data from cloud backup/device transfer and expose only explicit logical backup/restore as migration.

P5 is a reliability PoC, not a delivery slice: it implements and proves the storage-level machinery in `:core:data` — non-destructive legacy bootstrap, the ZIP logical format, manifest, both preflight passes, record-level staging, exact-candidate activation, same-repository handoff, and startup gate order — without export/restore UI, SAF picker, progress/cancel UX, confirmation dialogs, CSV, or shared-draft journeys. Those product surfaces belong to M6 (Journeys 11–13).

The format, limits, activation protocol, and legacy bootstrap are defined by [data and storage](../../../architecture/data-and-storage.md), [ADR 0003](../../../architecture/decisions/0003-generation-based-restore.md), and [ADR 0010](../../../architecture/decisions/0010-generation-bootstrap-and-live-session-handoff.md); P5 is their first executable implementation on the reference device, against the v2 schema, with the fault evidence the testing strategy maps to P5. P5 introduces no Room schema change: `databaseVersion` stays 2 and the committed schema exports stay `1.json` + `2.json`. It does perform the separately approved persistent-layout/recovery-record migration from P3/P4 into the generation layout.

## 4. Behavior scope

### 4.1 Backup generation and publication boundary

Export follows the one ordered reliability boundary of [data and storage](../../../architecture/data-and-storage.md): consistent logical read → stream and hash JSONL and attachments → write the manifest last → validate the complete package → publish.

- The consistent logical read opens the v2 Room database read-only on a single snapshot point: every table read from the same transaction so entity references, facts, finance children, relations, catalog facts, attachment metadata, and attachment links cannot mix generations mid-export.
- Every payload entry is streamed once and hashed with SHA-256 as it is written; the manifest (written last) declares, per entry, `logicalType`, normalized relative `path`, byte `size`, `sha256`, and `recordCount` for JSONL datasets.
- After the manifest is written, the complete package is validated before it is visible anywhere: ZIP structure, entry enumeration, per-entry hashes against the manifest, and aggregate totals. Validation failure keeps the package temporary.
- **Private publication:** the package is written to an app-private temporary file on the same filesystem as the final path, validated, then published by atomic rename. An incomplete or unvalidated package is never present at the final path and is never listed as restorable.
- **SAF destination:** starting from a complete package validated in private storage, the exporter copies it to the provider target under the `BACKUP_SAF_COPY` protocol (section 4.6): the provider object is marked or named temporary/incomplete until the full copy closes and the destination verifies; provider rename is used when supported, otherwise the verified copy itself is the final state; the app's incomplete marker clears only after full copy and destination verification succeed. Partial residue remains marked or named incomplete, is deleted best-effort, is never reported as success, and is never listed as restorable.

Export is a read-only operation over the current generation: it never mutates facts, relations, or attachment state. An export failure leaves the current vault exactly unchanged.

### 4.2 ZIP logical format

The portable backup is a ZIP with `manifest.json`, versioned JSONL datasets, and attachment binaries, exactly as [data and storage](../../../architecture/data-and-storage.md) defines:

- JSONL datasets for the facts the current v2 schema persists: `EntityRef`, `Account`, `Transaction`, `AccountEntry`, `Note`, `TransactionNoteAssociation`, `Attachment`, and `AttachmentLink` (attachment ownership) — eight datasets for the eight v2 tables. The remaining data-and-storage contract datasets — `Category`, `CategoryAllocation`, `Project`, `Tag`, and `EntityTag` — are introduced when the M2–M4 schema changes create those tables, as backward-compatible `formatVersion = 1` extensions: a new `logicalType` whose record shape is pinned by the owning MVP slice spec, which the restore reader must implement before accepting a manifest declaring it; P5's reader rejects any `logicalType` it does not implement, including the not-yet-existing catalog datasets. P5 pins the JSONL record shapes for the eight current datasets.
- Attachment binaries at `attachments/<sha256>` where `<sha256>` is the canonical `contentIdentity`.
- `transactions.csv` is never embedded in the logical restore ZIP. CSV is a separate M6 export artifact and is never a restore input.
- **`formatVersion` is fixed to `1` at this first implementation of the format**; a structural format change is a compatibility decision and requires a new ADR per the engineering conventions, and `databaseSchemaVersion` remains provenance and debugging information and never rejects a logically supported backup. Within a structurally supported format, every declared and encountered `nameKeyVersion` is an independent required sub-contract the restore reader must implement; version 1 is the only currently existing version (ADR 0004).
- The manifest includes `formatVersion`, `databaseSchemaVersion`, `appVersion`, `createdAt`, `backupId`, `hashAlgorithm=SHA-256`, and the sorted set `catalogNameKeyVersions` summarizing the versions used by catalog records (empty when the backup contains no catalog records). It contains one descriptor for every payload entry except `manifest.json` itself. The manifest contains no device identifier or hardware IDs.

The data-and-storage contract requires catalog logical records to be complete rather than display-only (Category/Tag identity + `displayName` + `nameKey` + `nameKeyVersion` + state + nullable `archivedAt`; Project identity + `displayName` + `nameKey` + `nameKeyVersion` with archive metadata carried by the matching `EntityRef.deletedAt`), with the manifest summary not repeating per-record catalog content so every catalog record stays self-describing through its own `nameKeyVersion`; this becomes binding evidence when the M2–M4 catalog tables and datasets land, and P5's manifest/reader framework (the `catalogNameKeyVersions` contract and the supported-version checks of section 4.3) implements the mechanism now. Attachment JSONL records carry the canonical `Attachment` metadata including the zero-link cleanup-pending `deletedAt` state; `AttachmentLink` records carry every ownership edge. Soft-deleted history (`EntityRef.deletedAt`) is exported and restored; only the complete logical backup preserves it.

### 4.3 Restore preflight resource limits

The binding MVP input limits of [data and storage](../../../architecture/data-and-storage.md) are P5 acceptance gates, not deferred:

- at most 100,000 ZIP entries, including `manifest.json`;
- each normalized relative path at most 240 bytes in UTF-8 and relative; absolute paths, traversal segments, duplicate normalized paths, and duplicate normalized `logicalType`/`path` pairs rejected;
- each attachment payload at most 512 MiB uncompressed;
- each structured-data entry (including JSONL) at most 1 GiB uncompressed;
- total uncompressed bytes across all ZIP entries at most `min(20 GiB, available app-private staging space − 1 GiB safety reserve)`; a zero-or-negative space-derived value rejects preflight before import;
- each non-empty entry and the non-empty archive as a whole have an uncompressed-to-compressed ratio of at most 200:1; a zero-uncompressed-byte entry has ratio zero and is allowed when otherwise valid; a non-empty payload with a zero compressed-byte denominator is rejected; an archive containing only zero-byte payloads has ratio zero.

Preflight enforces these limits twice:

1. **Declaration pass** combines the manifest descriptors with ZIP-directory metadata: declared entry count, normalized UTF-8 path bytes, manifest `size` plus ZIP-declared uncompressed/compressed sizes, per-entry ratios, and aggregate values — all checked before staging.
2. **Streaming pass** independently counts actual entry count and actual compressed and uncompressed bytes without trusting manifest or ZIP headers. Actual streamed bytes may never exceed the manifest or ZIP-declared size, the per-entry limit, the aggregate limit, or the available-space budget; crossing any limit fails immediately, closes the stream, leaves the current vault unchanged, reports no restore success, and leaves temporary staging content identifiable for safe cleanup. A declared value below actual bytes is corruption, not a reason to expand the budget.

Import additionally validates, per [data and storage](../../../architecture/data-and-storage.md): `formatVersion`, every manifest-declared catalog normalization version, normalized paths with no traversal, duplicate normalized paths, duplicate normalized `logicalType`/`path` pairs, duplicate singleton JSONL `logicalType` values, declared and actual size limits, SHA-256 values, JSONL record counts, exactly one canonical Attachment record and one matching blob per referenced SHA-256, no duplicate Attachment rows sharing a `contentIdentity`, every link targeting the canonical ID, and rejection of missing, extra, mismatched, or corrupt attachment content. During streaming, the encountered per-record `nameKeyVersion` set must exactly match the manifest summary; an omitted, extra, or unsupported version rejects the candidate.

The restore process does not use `databaseSchemaVersion` as a compatibility gate and does not accept any path, payload, count, catalog normalization version, or catalog invariant that fails validation.

### 4.4 Record-level preflight and catalog staging validation

Restore has both the manifest/resource pass of section 4.3 and a record-level candidate pass. Insufficient temporary storage is a blocking preflight error. The record-level pass imports database and attachment content into an isolated, non-active staging generation before overwrite confirmation is enabled, validating record counts, foreign keys, the `EntityRef` XOR invariant, the finance transaction matrix, resulting balances, associations, endpoint ownership, attachment hashes, and the complete catalog contract. The current generation remains untouched.

Catalog staging validation is mandatory and ordered before the activation-record switch. For the current v2 schema no catalog table exists, so P5 proves the framework: every manifest-declared and record-level catalog normalization version is checked against the reader's supported set, an unknown or unimplemented `logicalType` rejects the candidate, and the `catalogNameKeyVersions` contract of section 4.3 is enforced exactly. The eight catalog rules of [data and storage](../../../architecture/data-and-storage.md) — trimmed 1–40-code-point `displayName`; first-level-only Category; declared/supported `nameKeyVersion`; exact key recomputation; per-type active-plus-archived uniqueness; valid `ACTIVE`/`ARCHIVED` state with consistent `archivedAt` and Project archive only in `EntityRef.deletedAt`; every allocation/association/assignment targeting an existing catalog fact including archived targets; and current names/states/archive metadata matching the exported records — become binding when the M2–M4 schema changes introduce the catalog tables and datasets, and the owning MVP slices carry that evidence.

Any failure rejects preflight for the complete candidate before overwrite confirmation and activation, leaves the current vault unchanged, reports no restore success, and leaves staging identifiable for deterministic safe cleanup. No invalid catalog subset can be skipped, repaired implicitly, or partially restored; no implementation may drop a row or re-derive a key to make a candidate pass.

### 4.5 Generation activation and startup gate

The generation-based overwrite restore of [ADR 0003](../../../architecture/decisions/0003-generation-based-restore.md) is implemented and proven in P5:

- **Storage convention:** generation-specific database names; `files/vaults/<generationId>/attachments/` for generation-specific content; one app-private, atomically persisted activation/recovery record at `files/recovery/activation-recovery-v1.json` whose normal P5 form is `recordVersion = 2` — the P3 `migrationRecoveryState` portion is carried unchanged in meaning, and a new generation-activation portion is added containing `activeGenerationId`, nullable `previousGenerationId`, nullable `candidateGenerationId`, nullable `retiringGenerationId`, and `state` (`HEALTHY` or `PENDING`). The `migrationRecoveryState` gate is checked first at startup. The normal-operation reader supports exactly version 2; version 1 is accepted only by ADR 0010's one-time bootstrap reader.
- **Legacy-layout bootstrap:** before normal v2 startup, classify without Room. A v1 record first completes pending P3 recovery and any required approved v1→v2 Room migration on the legacy layout; malformed input fails closed. Bootstrap checkpoints/closes the database, records logical state and the post-checkpoint byte baseline, copies the database plus complete root attachment tree into one incomplete-marked unreferenced generation, validates it, then atomically publishes the healthy v2 pointer. Copy/validation/publication cannot change the frozen source baseline. No-record legacy data follows bootstrap; only no record plus no legacy data is fresh. Pre-write crashes retain legacy authority; post-write crashes retain only the complete generation. P5 never deletes the source.
- **The activation protocol of [data and storage](../../../architecture/data-and-storage.md) (the decision owned by [ADR 0003](../../../architecture/decisions/0003-generation-based-restore.md)), steps 0–6**, is proven end to end: step 0 preflight maintenance (a new restore requires all three nullable generation fields clear; pending retirement completes idempotently first or returns a typed maintenance error that blocks only this restore, never active reads); step 1 stage (the validated staging generation is imported but not yet referenced); step 2 activate pending (one atomic record write to `PENDING` with `C` active, `O` previous, `C` candidate); step 3 open-and-resolve gate (the confirmation path immediately invokes the same resolver used by a later cold startup; either path revalidates candidate checksums, catalog name/lifecycle/version rules, historical catalog references, and all other domain invariants before normal use); step 4 confirm healthy (one atomic transition: `C` active, `O` retiring, previous/candidate cleared, `HEALTHY`); step 5 rollback (one atomic record write restoring `O` active and making the failed candidate `C` retiring); step 6 retire (per-generation lock, all handles closed, `R` differs from every pointer, delete or confirm absent, then atomically clear `retiringGenerationId`).
- **Every step is idempotent**, including validation recovery, rollback, quarantine, orphan scanning, and retirement. A crash before the activation-record switch leaves the old generation active; a crash after the switch leaves a durable `PENDING` record so startup repeats validation; confirm and rollback each update the record atomically so a crash exposes either the whole `PENDING` record or the whole resulting `HEALTHY` record, never mixed fields; retirement crash windows retry or complete from observed absence.
- **Startup gate order:** every startup classifies/completes legacy bootstrap first when needed, then resolves the version-2 `migrationRecoveryState` gate, then the generation-activation gate, before Room or SQLite opens the active generation. **A truly fresh install has neither record nor legacy vault data: the gate atomically creates the initial generation — writing the record with a generated `activeGenerationId` and `state = HEALTHY` — before Room opens it**, so the first active generation is always pointer-owned and never a sidecar-less orphan. A pending activation is always resolved synchronously; normal Room opening remains blocked while either record is pending.
- **Single session, operation gate, and live handoff:** a process-wide registry keyed by canonical vault root serializes first open/bootstrap and returns one production repository identity; independent live bindings to one vault are forbidden. Ordinary calls take its shared gate; bootstrap/activation/rebind take exclusive. The repository atomically references a complete generation binding. `stageRestore` returns a process-local receipt-bound handle. Confirmation recomputes it, drains calls, closes O, writes `PENDING`, runs the cold-start resolver, constructs C or O's binding, and swaps before return. After `PENDING`, resolution is non-cancellable; process death invalidates the staged handle.
- **Orphan scanning:** safe startup may scan generation directories; it never deletes a directory named by any activation-record generation field; complete or incomplete directories referenced by no pointer are orphan candidates cleaned idempotently under the same per-generation exclusion used by restore.
- **Maintenance:** retirement is non-user-blocking safety maintenance; correctness never depends on WorkManager (M7 owns its scheduling). The restore path itself is synchronous: the next restore preflight must finish or fail retirement before staging, and an unresolved retirement cannot be overwritten by another restore.

Any failure before activation leaves the current generation active and quarantines or marks staging for safe cleanup. Restore never exposes a partial replacement. Restore is a generation activation, not a database migration.

### 4.6 Backup and restore fault evidence

The named testing-strategy mappings are P5 gates; every injected fail point runs the three-scenario protocol (fail once then restart; fail repeatedly without bypassing safety; complete then repeat the handler for idempotence):

- **`GENERATION_BOOTSTRAP`:** run healthy/recovered v1 records, every pending v1 migration stage, no-record legacy data, and truly fresh install; interrupt around legacy recovery/migration, WAL checkpoint, database/attachment copy, candidate validation, and v2 write. Before publication restart uses the authoritative legacy source; after it startup uses only the complete generation. Evidence proves pre-checkpoint logical equality, post-checkpoint frozen hashes unchanged by later steps, identifiable residue, and no legacy deletion.
- **`BACKUP_STREAM_AND_PUBLISH`:** interrupt every versioned JSONL stream and attachment-binary stream before first write, mid-entry, after final payload write, during flush/close, and immediately before manifest creation; interrupt manifest write before first byte, mid-write, after final write but before close, and before/after private atomic rename. In every case the package remains private temporary/incomplete, is never visible in the restorable list, and is never reported as success; cleanup and retry identify the residue deterministically.
- **`BACKUP_SAF_COPY`:** starting from a complete privately validated package, interrupt SAF target creation, first/middle/final copy chunks, provider flush/close, destination verification, provider rename when supported, and incomplete-marker clearing. P5 implements the provider target as an injectable interface (section 4.8); the product SAF `DocumentFile` implementation is M6's, so the P5 matrix proves the copy protocol on a test-scoped provider target that exposes the same create/copy/flush/close/verify/rename/marker steps. A partial provider object remains marked or named incomplete, is never listed or reported as complete, and is eligible for best-effort cleanup or an unambiguous retry; only a fully copied and reverified provider object may clear the incomplete marker and become visible.
- **`RESTORE_ACTIVATION`:** cover success and rollback transitions into `retiringGenerationId`, exact staged-handle binding, stale/mismatched/repeated handles, shared operations draining before the exclusive switch, every deletion/clear crash window, a new restore blocked by unresolved retirement, pointer-protected orphan scanning, pending activation, immediate resolver reuse, and repeated cold startup; after success the same repository instance reads/writes only the candidate, after rollback it reads/writes only the original, and Room/shell never bypass a pending migration/activation gate. The retirement handler is proven idempotent and re-entrant under the three-scenario protocol so that a retry racing synchronous preflight (the testing strategy's WorkManager-racing boundary, whose scheduling stays M7's) can never duplicate an effect or corrupt a generation pointer.
- **Catalog staging and revalidation fault injection:** the required failure test points of data and storage — interruption while recomputing catalog keys, checking name-key versions/uniqueness, validating lifecycle metadata, or resolving historical catalog references in staging and startup revalidation — run the three-scenario protocol under the `RESTORE_ACTIVATION` mapping (staging validation is the preflight side, startup revalidation is activation step 3); every interruption leaves the current vault unchanged, reports no success, and leaves staging identifiable for safe cleanup.
- **Applicable `MIGRATION_RECOVERY`:** after legacy classification/bootstrap, the migration gate precedes generation activation; restore cannot pass a `MIGRATION_RECOVERY_PENDING` record, and the resolver completes recorded recovery first. A restored vault opens on v2 without a logical `databaseSchemaVersion` gate. The full N-1/N-2 matrix remains M7's, per ADR 0007.

### 4.7 Android system backup exclusion

The manifest already sets `android:allowBackup="false"` and references both rule files, but the current XML excludes only `root` and is insufficient. P5 updates both rules to exclude all nine Android backup domains — `root`, `file`, `database`, `sharedpref`, `external`, `device_root`, `device_file`, `device_database`, and `device_sharedpref` — under both `cloud-backup` and `device-transfer` in `dataExtractionRules`, and under `fullBackupContent` for compatible handling. Source, merged, and packaged inspection proves the exact set and no network capability. Android 16 QPR2/API 36.1 adds cross-platform-transfer configuration, but P5's frozen compileSdk is 36.0; P5 does not silently change toolchain to configure it. Any later 36.1+ baseline must add its supported exclusion and policy gate before approval. Only explicit logical backup/restore is supported migration.

### 4.8 Typed surface extension

The P1–P4 public surface is unchanged except for additive backup/restore operations in `:core:data`:

- **Export:** typed export entry points over the current active generation — one for private publication, one for a SAF/provider target. Outcomes are typed: success carries the published artifact identity; failures carry a precise classification — IO failure at a named stage, validation failure of the generated package, or provider failure at a named `BACKUP_SAF_COPY` stage. Export is read-only over the active generation: pending retirement never blocks it (per [data and storage](../../../architecture/data-and-storage.md), only a new restore is blocked by unresolved retirement). No outcome reports success when the package was not fully validated and published.
- **Restore:** typed restore entry points — stage (preflight + record-level candidate pass into an isolated staging generation), confirm with the exact returned staged handle (exclusive activation/rebind under section 4.5, which may return maintenance-pending or candidate-mismatch), and the startup-time resolution shared by confirmation and cold open. Outcomes are typed: success only after the same repository instance is rebound to the healthy candidate; rejections carry the precise preflight category (resource limit, format, manifest, record syntax, catalog, foreign key, finance, attachment, XOR, candidate mismatch, or corruption); rollback rebinds the original before returning failure; no outcome reports success on a partial replacement.
- **Provider target abstraction:** the SAF copy steps (create, copy chunk, flush/close, verify, rename when supported, incomplete marker) are exposed as an injectable interface so the `BACKUP_SAF_COPY` matrix runs deterministically; the M6 UI wires the real `DocumentFile` provider.
- **Startup extension:** the existing open-and-resolve flow resolves the migration record first and then the generation-activation record before Room opens; no UI or shell path can bypass either gate.
- **Operation-gate boundary:** the repository-wide gate and candidate registry are module-internal. Callers cannot write activation state, supply a physical generation path, or bypass exact-handle verification; ordinary P1–P4 calls keep their signatures and participate in the shared gate internally.
- The precise members, names, and package placement are pinned normatively in the plan; the spec fixes only the semantics above. Every existing P1–P4 outcome is unchanged; P5 adds no renamed or re-meant outcome.

### 4.9 Deferred to later slices

Explicitly not part of P5:

- The export/restore UI: destination picker, SAF document picker, progress modal, cancel race, restore confirmation dialog, and the `Phase.*` ViewModel states (M6; interaction rules and the fifth critical Compose flow).
- CSV export (Journey 12) and shared text/image drafts (Journey 13) (M6). P5's ZIP format never contains CSV, but the CSV exporter itself is M6's, and the testing strategy's separate CSV contract test is not P5 evidence.
- The real SAF `DocumentFile` provider implementation and its UI journeys (M6). P5 proves the copy protocol on the injectable provider abstraction only.
- WorkManager scheduling of retirement and any deferred maintenance scheduling (M7).
- Deletion of the P3/P4 root database, sidecars, root attachment tree, or version-1 migration artifacts after successful bootstrap; P5 retains them, and later cleanup requires separate authorization.
- The full N-1/N-2 migration matrix and the complete `MIGRATION_RECOVERY` fault suite (M7).
- Encryption of backups, cloud sync, or any additional migration path (explicit exclusions of data and storage).

That clause is P5 evidence through criterion 1 and the canonical round-trip fixture (section 6).
- Any change to the v2 schema, committed schema exports, public surface beyond section 4.8, or module graph. The explicitly required nine-domain backup-rule correction is in scope.

## 5. Invariants and acceptance criteria

### 5.1 Invariants in scope

- The complete logical backup is the only supported restore input; CSV, Android cloud backup, system transfer, and live SQLite/WAL copies are never restore inputs.
- The ZIP is exactly `manifest.json` + the eight current-schema JSONL datasets (section 4.2) + `attachments/<sha256>`; CSV is never inside it, and no device identifier or hardware ID is inside it.
- The manifest is written last and describes the package exactly (per-entry `logicalType`, path, size, SHA-256, and `recordCount`); the package is validated before it is visible anywhere.
- `formatVersion = 1` is fixed at this first implementation; a structural format change is a compatibility decision requiring a new ADR; `databaseSchemaVersion` is provenance only; every declared/encountered `nameKeyVersion` is an independent required sub-contract.
- Every binding resource limit is enforced twice (declared pass and streaming pass); crossing any limit leaves the current vault unchanged, reports no success, and leaves staging identifiable for safe cleanup.
- The current generation remains untouched through staging; activation is one atomic record switch; a crash exposes either the whole `PENDING` record or the whole resulting `HEALTHY` record, never mixed fields.
- Legacy bootstrap never mutates or deletes the legacy source: before the v2 record write the v1/root layout remains authoritative, after it only a complete validated pointer-owned generation is active.
- Every repository operation participates in one shared/exclusive gate; confirmation binds the exact staged handle, closes old Room/WAL/SHM handles before `PENDING`, and returns only after the same repository instance is rebound to the healthy candidate or rolled-back original.
- Every startup resolves the migration gate before the generation gate before Room; neither gate is bypassable by UI or shell.
- No generation directory named by an activation-record pointer is ever deleted; orphan cleanup is idempotent and pointer-aware.
- Restored attachment state is canonical: one `Attachment` record and one matching blob per referenced SHA-256, no duplicate `contentIdentity`, every link targeting the canonical ID.
- Soft-deleted history, every relation, and zero-link cleanup-pending attachment state survive the round trip; the catalog-dataset contract (complete logical records, self-describing `nameKeyVersion`, archived-history preservation) is binding when the M2–M4 tables land and the framework is proven now.

### 5.2 Acceptance criteria

The slice passes only when all of the following have evidence in `verification.md`:

1. **Complete logical round trip.** The current-schema fixture exports to a validated ZIP; the isolated vault is wiped/overwritten; the ZIP stages; confirmation presents the exact receipt-bound handle and crosses the common pending resolver; normalized comparison matches every persisted field, relation, balance, soft-deleted fact, attachment owner/size/SHA-256, and the catalog framework. The app restarts and repeats integrity/balance checks. Two owners share one canonical duplicate-content attachment, preserving one record and both links.
2. **Manifest contract.** A generated backup's manifest declares `formatVersion = 1`, the current `databaseSchemaVersion` and `appVersion`, `createdAt`, `backupId`, `hashAlgorithm=SHA-256`, the sorted `catalogNameKeyVersions` set (empty for a fixture with no catalog records), and one descriptor per payload entry except `manifest.json`, with per-entry `logicalType`, normalized relative `path`, byte `size`, `sha256`, and `recordCount` for JSONL datasets; recomputing every entry hash against the manifest matches exactly; the manifest contains no device identifier.
3. **Generation boundary and publication.** Every JSONL dataset and attachment blob is streamed and hashed once from a single consistent logical read; the manifest is written last; the complete package is validated before any publication step; private publication is an atomic rename on the same filesystem with no visible final path before validation; an export failure leaves the current vault unchanged.
4. **`BACKUP_STREAM_AND_PUBLISH` matrix.** Every fail point of section 4.6 runs the three-scenario protocol; evidence records the injected boundary, observed durable state, visibility/success assertion, residue classification, restart/retry outcome, and cleanup outcome for each named fail point.
5. **`BACKUP_SAF_COPY` matrix.** From a complete privately validated package, every provider fail point (create, first/middle/final chunks, flush/close, verify, rename when supported, marker clearing) runs the three-scenario protocol; a partial provider object stays incomplete-marked, is never listed/reported complete, and cleanup/retry is deterministic; only a fully copied and reverified object clears the marker.
6. **Malicious ZIP — declaration pass.** Exact-limit and over-limit fixtures for every binding limit (100,000/100,001 entries; 240/241-byte normalized paths; absolute/traversal/duplicate paths; duplicate `logicalType`/`path` pairs; duplicate singleton JSONL `logicalType` values; 512 MiB/512 MiB+1 attachment; 1 GiB/1 GiB+1 structured entry; 20 GiB and the space-derived aggregate at and below the 1 GiB reserve; ratio exactly 200:1 and above; zero-byte entries/archive; non-empty payload with zero compressed-byte denominator) are rejected before staging with the current vault unchanged, no success, and identifiable temporary state; every exact-limit valid fixture proceeds to the remaining validation gates.
7. **Malicious ZIP — streaming pass.** The streaming pass independently counts actual entries and bytes without trusting manifest or ZIP headers; declared-below-actual sizes, mid-stream per-entry/aggregate crossings, stream exhaustion, short reads, and low-space change during staging each fail immediately with the stream closed, the current vault unchanged, no success, and identifiable staging for cleanup/retry.
8. **Record-level preflight and staging validation.** Preflight validates record counts, foreign keys, XOR identity, the finance matrix, resulting balances, associations, endpoint ownership, attachment hashes, and the catalog-contract framework: a manifest declaring a `logicalType` the reader does not implement (including the not-yet-existing catalog datasets) or a `catalogNameKeyVersions`/record-level `nameKeyVersion` outside the supported set rejects the complete candidate before confirmation and activation, with the current vault unchanged, no success, and identifiable staging. The full catalog data matrix (duplicate normalized names, key recomputation, state/lifecycle metadata, historical references, archived-history preservation) belongs to the M2–M4 slices that introduce the catalog tables and datasets and becomes their backup/restore evidence; the catalog staging/revalidation fault injection of section 4.6 runs the three-scenario protocol now.
9. **`RESTORE_ACTIVATION` matrix.** Steps 0–6 cover exact handle verification, success/rollback, immediate and cold-start resolver paths, complete binding swaps, and every crash window before/after `PENDING`, validation, rollback, healthy transitions, retirement deletion, and pointer clear. External readers see only complete O or C; unresolved retirement blocks only a new restore; referenced generations are protected; no partial success is reported.
10. **Migration ownership and applicable `MIGRATION_RECOVERY`.** Startup first classifies/completes legacy bootstrap, then resolves `migrationRecoveryState`, then generation activation, then Room. Restore cannot pass a pending migration gate; the restored vault opens on v2 without using `databaseSchemaVersion` as a gate; the common resolver handles pending activation during immediate confirmation or cold startup and never opens mixed state. The full N-1/N-2 matrix remains M7's.
11. **Android system backup exclusion.** Source, merged, and final-APK inspection shows `allowBackup=false`, both rule references, and no network capability. Packaged `dataExtractionRules` contains exactly the nine-domain exclusion set under both cloud and device-transfer; packaged `fullBackupContent` contains the same exact set. The only migration surface is explicit logical backup/restore.
12. **Surface and schema machine checks.** (a) The schema contract test passes against the committed `2.json`: `databaseVersion = 2`, all eight tables unchanged, no migration added. (b) The `:core:data` public-surface allowlist is updated to the P5 normative list (the additive backup/restore operations of section 4.8 only) and matches exactly in both directions. (c) `apiBoundaryCheck` passes, with negative fixtures proving no path can write activation state, stage a restore, publish a backup, or bypass the startup gates outside the typed surface.
13. **Regression.** `./gradlew clean check` passes (module graph, build, lint unchanged), and the app still installs and launches on the reference device.
14. **Legacy bootstrap and live-session handoff.** Bootstrap fixtures/fail points prove the pre-checkpoint logical and frozen post-checkpoint byte contracts with no deletion. Concurrent production opens of one canonical root execute bootstrap once and return one repository identity. Confirmation rejects invalid handles, drains calls, closes O before `PENDING`, runs non-cancellably, and proves that sole repository's complete binding targets only C after success or O after rollback; isolated test roots remain independent.

## 6. Test evidence requirements

- **JVM unit tests** cover the pure pipeline logic in `:core:data`'s test source set: ZIP path normalization and the declared-pass decision table, the streaming-pass counting logic, manifest construction/parsing (including descriptor/record-count/version-set consistency), JSONL record encoding/decoding round trips including boundary timestamps and Unicode, resource-limit arithmetic, the catalog key-recomputation checker, and the activation-record state machine transitions. Property tests on the JVM prove round-trip stability of the JSONL codec over generated histories with fixed seeds recorded on failure.
- **The canonical round-trip fixture** contains every entity type the v2 schema persists — EntityRef for each fact, Account, Transaction, AccountEntry, Note, TransactionNoteAssociation (the transaction-note relation), Attachment, and AttachmentLink — with each transaction type, multi-allocation income/expense, bidirectional transaction-note associations, two owners sharing one canonical duplicate-content attachment, soft-deleted facts (via `EntityRef.deletedAt`), Unicode account names, and boundary timestamps. This mirrors the testing strategy's canonical fixture for the entities the current schema persists; the strategy fixture's catalog items (Category/Tag/Project with name/key/version/lifecycle and historical references) become part of the M2–M4 round-trip evidence when those tables and datasets land. Comparison ignores representation-only ordering where the format declares it irrelevant but compares stable IDs and every logical field.
- **Instrumented tests on the reference device** prove the persisted behavior through the public repository surface: the complete round trip (export → verify → wipe/overwrite → restore → startup gate → comparison → second restart), the `BACKUP_STREAM_AND_PUBLISH` matrix, the `BACKUP_SAF_COPY` matrix on the injectable provider target, the malicious-ZIP declared and streaming matrices (sparse/generated streams rather than repository fixtures of physical multi-GiB size), the catalog-contract framework fixtures (unknown-`logicalType` and unsupported-version rejection; the catalog data matrix is M2–M4 evidence), the full `RESTORE_ACTIVATION` protocol, and the startup gate order.
- **Legacy bootstrap and handoff tests on the reference device** use copied P3/P4 fixtures, never the developer's live vault. They cover recovery/migration, no-record/fresh classification, pre-checkpoint logical equality, frozen post-checkpoint hashes, all crash windows, single-session identity, exact candidate binding, exclusive drain, complete-binding success/rollback, and cold recovery after `PENDING`.
- **Every injected fail point** runs at least three scenarios per the testing strategy: fail once then restart; fail repeatedly without bypassing safety; and complete then repeat the handler to prove idempotence. Sidecar interruption coverage applies wherever a fail point touches the migration/activation records; activation coverage proves both successful and rollback retirement paths.
- **Fault-injection evidence** names every fail point and the mapping it belongs to — `GENERATION_BOOTSTRAP`, `BACKUP_STREAM_AND_PUBLISH`, `BACKUP_SAF_COPY`, `RESTORE_ACTIVATION`, or the applicable `MIGRATION_RECOVERY` — with the injected boundary, observed durable state, visibility/success assertion, residue classification, restart/retry outcome, and cleanup outcome; a summary such as "fault tests passed" is insufficient. Bootstrap evidence also records legacy/v2 record hashes, source/candidate vault hashes, pointer state, repository backing generation, and proof of no legacy deletion. ZIP-limit evidence enumerates every declared/actual boundary and proves unchanged current-vault hash plus temporary cleanup state. System-policy evidence includes source manifest, merged manifest, final-APK manifest, and packaged `data_extraction_rules`/`backup_rules` contents.
- `verification.md` maps every acceptance criterion and the roadmap P5 exit gate to concrete commands and results in the testing strategy's `Command`, `Environment`, `Result`, `Remaining risk` format; a build-only result cannot stand in for the required round trip, matrices, or measurements.

## 7. Non-goals

P5 explicitly does not:

- Implement any export/restore UI, ViewModel, navigation, picker, progress modal, confirmation dialog, or `Phase.*` state (M6).
- Implement CSV export (Journey 12) or shared text/image drafts (Journey 13) (M6); the ZIP format never contains CSV, but the CSV exporter is M6's.
- Implement the real SAF `DocumentFile` provider wiring (M6); P5 proves the copy protocol on the injectable provider abstraction.
- Add encryption, cloud sync, or any migration path beyond the explicit logical backup/restore.
- Change the v2 Room schema, add a Room schema migration, change the module graph, or introduce a new dependency. The ADR-0010 persistent-layout bootstrap is the only approved compatibility migration in P5.
- Schedule retirement or any maintenance via WorkManager (M7), or run the full N-1/N-2 migration matrix and complete `MIGRATION_RECOVERY` fault suite (M7).
- Change any P1–P4 outcome, table, or public declaration that is not the additive backup/restore surface of section 4.8.
- Silently diverge from any core-document fact. If implementation exposes a conflict with a core document, the documentation-first protocol applies before any code change and the spec returns to review.

## 8. Dependency review boundary

Every dependency introduced by P5 is recorded at plan approval per the engineering conventions: version, license, maintenance evidence, compatibility impact, and removal path. No new dependency is anticipated — `java.util.zip`, `java.security.MessageDigest`, the hand-rolled strict JSONL/manifest codec, `java.nio.file`/`File`, and the hand-rolled generators are platform/JDK built-ins — and the P1–P4 pinned toolchain is reused. A dependency is rejected when its license is incompatible, its maintenance status is unknown, it requires excessive permissions, it introduces undisclosed network behavior, or no practical removal path exists. No ads, analytics, crash-reporting, or closed-source tracking SDK.

## 9. Risks

- **First implementation of the logical format.** The ZIP/manifest/JSONL format and the two-pass preflight are implemented for the first time; the JVM codec properties and the declared/streaming matrices bound the risk, and `formatVersion = 1` makes a future structural change an explicit ADR decision.
- **Device IO timing and large-fixture runs.** The round trip and the malicious-ZIP matrices run on the reference device; the plan must account for device time and USB stability, as in P2/P3, and use sparse/generated streams for the multi-GiB boundary cases.
- **Provider behavior differences.** The `BACKUP_SAF_COPY` matrix proves the copy protocol on an injectable target; the real provider (M6) can behave differently in rename support or verification semantics, so P5 records the protocol contract the M6 implementation must satisfy.
- **Activation-record atomicity.** The activation record is the single point of durability for generation switches; the steps-0–6 matrix and the idempotence protocol are acceptance evidence, and the record stays readable/atomically writable without Room.
- **Legacy bootstrap interruption.** The source database and attachments predate generation pointers; bootstrap therefore copies and validates them under the startup/exclusive gate, publishes only one atomic v2 pointer, and retains the source. The `GENERATION_BOOTSTRAP` matrix is blocking evidence.
- **Live repository handoff.** A durable pointer switch while old Room handles remain usable would lose later writes. ADR 0010's repository-wide gate, exact staged handle, close-before-`PENDING`, same-instance rebind, and concurrent handoff tests are blocking evidence.
- **Restore interplay with migration and cleaner state.** Restore must not fight a pending migration record or the attachment cleaner's per-hash serialization; the startup gate order and the applicable `MIGRATION_RECOVERY` evidence bound this, with the full matrix remaining M7's.
- **Catalog and finance validation depth in staging.** The staging pass validates the complete current-schema finance contract and the catalog reader/version framework before activation; the complete catalog data matrix becomes binding with the M2–M4 datasets, while criterion 8 and the current-schema fixture are P5 evidence.
- **Device system build.** The reference device runs API 36; behavior on the upgraded system is recorded at verification, not rejected — the same rule as P0–P4.
